# Security

Customer-authored VekoScript is untrusted code. The design keeps it away from anything it
could misuse and makes the Java platform the only authority over data.

## Threats and controls

| Threat | Control | Status |
| --- | --- | --- |
| Script reads or writes files, starts processes, opens network connections, reads environment variables | The language has no such constructs; the interpreter has no such capabilities; unknown names are compile errors | Tested (`scripts_have_no_ambient_authority`) |
| Script runs SQL or reaches the database | Scripts only make typed host calls (find, list, save, post, reverse, delete, balance); the Rust engine has no database driver; SQL is generated by Java from validated metadata with bound parameters | Tested (demo); by construction |
| Script loads native code, uses FFI, reflection or eval | Not part of the language or runtime | By construction |
| Infinite loop, deep recursion, huge collections or strings | Step, time, call-depth, collection, string, allocation and stack limits in the engine | Tested |
| Engine bug or limit bypass exhausts memory or hangs | Separate worker process; OS memory limit (Windows Job Object; Linux `RLIMIT_AS`); Java kills a worker that misses its wall-clock deadline and replaces it | Kill tested (`WorkerTimeoutTest`); OS limit implemented, not tested |
| Worker spawns children | Windows Job Object allows one active process | Implemented |
| User does more than their role allows | Capabilities from roles are checked by the engine before each host call and again by Java (the authority) for every operation, including those a script makes | Tested |
| Cross-tenant access | Applications belong to an organization; every request resolves the application by the token's organization; each application has its own schema | Tested (other organization gets 404) |
| Script tampers with platform-owned values (id, version, number, status, line numbers) | Scripts cannot assign them (VKS3017/VKS4015); Java also overwrites them after handlers | Script side tested; Java override implemented |
| Invalid data from a script or client | Java validates types, required fields, references and unique values before writing; posting intents are validated before movements are written | Tested |
| Lost update | Optimistic version check plus row locks | Tested |
| Double posting | Status check under row lock, transaction, unique index on active movements | Tested (concurrent) |
| Partial writes | One transaction per operation; outbox for after-commit work | Tested (injected storage failure) |
| Destructive schema change by mistake | Migration plan flags risky steps; deployment needs explicit, audited approval | Tested |
| Malformed or oversized protocol messages | Versioned envelopes; 32 MiB line limit; the platform kills a worker after a protocol error | Malformed and wrong-version messages tested; size limit implemented |

## Capabilities

Tokens are HS256 JWTs with `sub` (user), `org` (organization) and `roles`. Roles map to
capabilities in configuration (`vks.security.roles`):

| Capability | Allows |
| --- | --- |
| `catalog.read`, `catalog.write` | read; create, update, archive catalog items |
| `document.read`, `document.write` | read; create, update, archive documents |
| `document.post` | post and reverse documents |
| `register.read` | balances and movements |
| `*` | everything (role `admin`) |

Deploying an application requires the `admin` role. Scripts run with exactly the capabilities
of the user whose operation triggered them (after-commit handlers: the user who caused the
event).

## Not done yet

- Token issuing, key rotation and an identity provider are outside this service; it validates
  tokens signed with a shared secret (`VKS_JWT_SECRET`, at least 32 bytes).
- Row-level permissions (for example "only my warehouse") are Planned.
- The OS memory limit is not exercised by an automated test; macOS has no OS limit.
- Rate limiting per user or organization is Planned.
- No independent security review has been done.
